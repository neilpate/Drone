The custom nRF5340 flight-controller schematic is now ERC-clean and has a sourced BOM. ## 2026-08-24 — Telemetry split into high/low-rate frames, and ESC telemetry on the ground station

Yesterday's ESC serial-telemetry bring-up produced data the radio frame had no room for. Today that data reached the ground station, by splitting the drone-to-remote telemetry into two interleaved frames.

**High/low-rate frame split ([ADR 0027](decisions/0027-split-telemetry-high-low-rate.md)).** The single `Telemetry` type was already sitting on the 802.15.4 packet ceiling (~123 of ~125 usable bytes), with no room for the 31-byte ESC block. It became a tagged `TelemetryFrame { HighRate, LowRate }` enum. The **high-rate** frame (every ~10 ms round-trip) carries the flight-critical stream — raw IMU, filtered gyro, attitude, pilot command, controller demand, motor command, drone state — and drops the duplicated accelerometer the old frame wasted. The **low-rate** frame (every 10th cycle, ~10 Hz) carries housekeeping — CPU load, control mode, chip temperature, the full four-motor ESC telemetry, and the drone's *active* control gains echoed back for ground-truth logging. The aggregator stays the single publisher and now owns the interleave schedule; the remote relays whichever frame arrives; the ground station merges both into a running view so its plot, table and TSV log always see a complete row, with the low-rate columns simply updating at their slower cadence (the ADR's merge rule). A pleasant side effect of the leaner high-rate frame: the telemetry feels visibly snappier.

**ESC telemetry on the ground station.** Per-motor RPM, pack voltage, ESC temperature and consumed-mAh now appear as live plot series, table rows and TSV columns — the offline `analyze` tool is header-driven, so it kept working untouched. The ESC's current reading is discarded at the source: the AM32 shunt is uncalibrated and reads a constant ~9 A offset, which would otherwise also poison the consumed-mAh integral.

**Ground-station readout, tidied.** The flat telemetry list became labelled, fixed-width category boxes — System, Pilot command, Attitude, Accelerometer, Gyro, Controller demand, Motor command, ESC / power — stacked in vertical columns. Numeric values are right-justified in a fixed-width monospace field so a fluctuating reading no longer jitters, and the forced `+` sign was dropped.

## 2026-08-23 — DShot, the M4 asymmetry solved, first hover on the new drivetrain, and ESC serial telemetry

The weekend the motor drivetrain went digital. Outgoing **DShot300** replaced analog servo PWM — and in doing so solved a fault that had been fought for weeks; the drivetrain was retuned on the now-symmetric plant and hovered under control on DShot; and a full **ESC serial-telemetry** path was brought up for per-motor RPM, pack voltage and temperature.

**DShot, and the M4 mystery solved.** The persistent front-left (M4) thrust deficit — chased as a weak motor, a bad mount, worn props — was really **uncalibrated per-channel analog-PWM endpoints**: each ESC channel had a slightly different pulse-width-to-throttle mapping, so identical commands produced different thrust. DShot sends the same 11-bit digital value to every ESC, so the asymmetry vanished (left/right motor spread fell to ~0) the moment the protocol switched — a fault in the actuation layer, not the motor. The DShot300 driver reuses the motor driver's PWM0 + EasyDMA sequence machinery (one bit per PWM period, a looped 16-bit frame plus inter-frame gap so the ESC sees a continuous stream), with the host-tested frame encoder in `firmware-drone-core`; it became the sole motor path and analog PWM was removed. Gotchas recorded: AM32 latches its input protocol at power-up, so the ESC must be power-cycled after any PWM/DShot switch — and because AM32 self-resets on signal loss and can catch the floating-high signal pin at reboot and drop into its bootloader, the motor line wants a pull-down (or a power-cycle after each reflash).

**Retune, and the first hover on DShot.** With the plant symmetric, roll and pitch were re-tuned from scratch and settled matched at `kp` 0.15 / `kd` 0.16 / `ki` 0.02, baked into the firmware defaults so a fresh boot flies. The drone then made its **first controlled hover on the DShot drivetrain** — the highlight of the weekend, and the first flight with the front-left deficit finally gone rather than trimmed around.

**ESC serial telemetry — a bring-up in layers.** The direct measurement the earlier RPM-notch and M4 work needed is per-motor RPM, which the ESC's KISS telemetry wire carries (one-way, 115200, a 10-byte frame of temperature / voltage / current / mAh / eRPM / CRC8). Reading it cleanly meant peeling back several problems, each masking the next. The telemetry is **request-driven** — set the DShot telemetry-request bit and the ESC replies — but *holding* the bit makes AM32 re-trigger its own transmit faster than a 10-byte frame can leave the wire (~0.87 ms), corrupting its own output; the request has to be **pulsed**, one motor at a time. Even pulsed, each request yields a short **burst** of back-to-back frames with no idle gap inside it, so a fixed-length read can never align; the fix is to capture the whole burst (a 64-byte `read_until_idle`, idle-line-framed via UARTE + a spare TIMER + PPI on P0.26) and **CRC-scan** it for the one valid frame — the checksum does the alignment, and the collisions that fail it are simply dropped. Each decoded per-motor sample fans into a four-motor `ESCTelemetry` aggregate in the telemetry aggregator, and the motor task re-sends its last command on a keepalive tick so the request bit keeps flowing even at a static throttle. The result is solid **temperature, pack voltage and per-motor RPM**; current and consumed-mAh are only as trustworthy as the ESC's (evidently uncalibrated) shunt, which reads a constant offset. A [KISS telemetry frame diagram](learning/dshot-esc-telemetry-frame.svg) and the iFlight XING2 1404 [datasheet](../hardware/electrical/datasheets/iflight-xing2-1404-unibell-3800kv.md) — confirming 9N12P (12 poles, 6 pole pairs) for the eRPM to RPM conversion — were added, and [ADR 0027](decisions/0027-split-telemetry-high-low-rate.md) proposes splitting telemetry into high- and low-rate frames so the new ESC fields fit under the 802.15.4 packet ceiling.

## 2026-08-19 — Control maths verified, on-demand IMU recalibration, deeper analysis tooling, and Phase 4 kickoff

A consolidation session: no new flight, but the control path was proven correct end-to-end, a class of `Watch` first-publish bugs was cleared, the analysis tooling gained the checks to distinguish a firmware fault from a physical one, a proper test rig was built, and the custom-PCBA phase formally began.

**On-demand IMU recalibration — and two bugs behind it.** The ground station gained a **Zero IMU** button (disarmed only) that re-runs the accel/gyro calibration at any time, not just at boot. Making it actually work uncovered two independent faults. On the drone, the recalibrated offsets were captured into a `let`-shadowed binding inside an `if` block and silently discarded, so the read loop kept using the startup offsets — the telemetry never moved. On the remote, the reset was funnelled through the same `command` `Watch` as the ~100 Hz pilot-command stream, which clobbered the one-shot event before the 10 ms relay ever sampled it; it now travels as a dedicated `Signal` (single-observer event, per [ADR 0013](decisions/0013-async-communication-primitives.md)) that latches until consumed. A related **cold-boot hang** was also fixed: `Watch::get().await` blocks until a watch is *first* published, so an unseeded `imu_calibrate` (and `cpu_load`, whose only publisher is the load profiler) would park a task forever — both are now seeded at boot. The pattern is recorded so it stops recurring.

**The control maths, proven.** The `analyze` tool gained a **controller demand-vs-model** check: it reconstructs the Stabilized-mode P and D contributions from the logged attitude, filtered gyro, sticks and per-row gains, and compares them to the logged demand. P, D, and P+D all reconstruct to a correlation of **+1.0000** with machine-precision residual — the forward control path (estimate → error → PID → demand) is faithful to [ADR 0024](decisions/0024-control-law-angle-mode-pd.md), with no sign, scaling or gain bug. A separate **D-term isolation** (empirical D = logged demand − reconstructed P) confirms the derivative path as a pure-maths identity. The honest scope note stands: this verifies the forward maths only, not the estimator's accuracy, the mixer/motor path, or closed-loop stability.

**Telling a firmware fault from a physical one.** A persistent one-directional "fight" when the craft is held level, and a slow roll creep that re-zeroing only temporarily cured, prompted a **rest/drift diagnosis** in `analyze` — raw gyro bias, the attitude estimate versus the accelerometer's own gravity angle, drift slope, and temperature. A 44-second disarmed capture came back clean (drift ~0.002 °/s, gyro bias ~0.016 °/s, estimate tracking gravity to 0.06°, temperature flat), which *exonerated* the estimator and calibration at rest and pointed the creep at **motor-vibration rectification** — a dynamic, armed-only effect — rather than a static offset or thermal drift. The proper fix (RPM-tracking notch filtering) needs per-motor RPM, which is one of the drivers for the DShot work.

**A roll test rig.** To tune safely off the flight airframe, a single-axis rig that frees the roll axis was built, with the pivot on the centre of mass so gravity neither flatters nor fights the controller (a pendulum-stable rig hides instability; a neutral one shows the true closed-loop response). The rotate-and-release balance check doubles as the CoM finder.

**Phase 4 begins; two ADRs.** [ADR 0025](decisions/0025-persist-control-parameters-flash.md) commits to persisting the live-tuned `ControlSystemParameters` to internal flash (a log-structured store via `sequential-storage` over `Nvmc`, explicit disarmed-only save, default fallback), removing the reflash step from tuning and serving as a stepping stone onto the flash stack for a later OTA effort. [ADR 0026](decisions/0026-phase4-custom-pcba-nrf5340.md) commits Phase 4: the custom flight controller is built around a **pre-certified nRF5340 module** (Raytac MDBT53 class) on a hand-designed **KiCad** carrier, **turnkey-assembled** (which de-risks the QFN IMU and module joints and reopens LGA module options), using the nRF5340's **native USB-CDC** for the PC link plus an **external SWD probe** — no onboard DAPLink, collapsing the micro:bit's USB → interface-chip → UART path. A first v1 (micro:bit-era) and v2 (nRF5340, CopperPilot-generated draft) KiCad schematic were committed; the v2 draft was reviewed and flagged as not fab-ready (incomplete buck stage, sparse decoupling, unverified module/IMU pin maps).

**DShot, scoped and researched.** The next firmware step is outgoing **DShot** on the existing micro:bit, reusing the PWM + EasyDMA sequence machinery of the motor driver (a 16-entry duty table per frame, played one-shot). Its motivation is not just protocol modernity but the per-motor **eRPM telemetry** it enables — the direct measurement to settle whether M4 is genuinely weak. A [DShot bit-pattern diagram](learning/dshot-bit-pattern.svg) was added as learning material.

## 2026-08-08 — First free flight; the roll oscillation root-caused to the estimator; PID and flight-analysis tooling

The drone **flew** — first tethered hops, then its first **untethered** free flights on its own battery. Getting there meant closing the control law with an integral term, root-causing a stubborn roll oscillation that turned out to live in the *estimator* rather than the gains, and building the offline analysis tooling that made every capture legible.

**The integral term.** The angle-mode controller ([ADR 0024](decisions/0024-control-law-angle-mode-pd.md)) gained a per-axis **integral** on roll and pitch (yaw stays rate-P), turning the PD into a PID that trims out the steady-state lean P alone leaves. It is stored in *contribution units* (`I += ki · error/max_tilt · dt`, and the output adds `I` directly), which makes live `ki` retuning bumpless — changing the gain reweights only future increments, never the accumulated value. Anti-windup is conditional integration (the increment is skipped only when it would drive further into the ±`MAX_INTEGRAL` rail, so recovery is never blocked), and the integral resets to zero at zero throttle, clearing accumulated authority on the ground and at disarm. Pure logic in `firmware-drone-core` with ten new stateful tests — accumulation, saturation, unwind, idle reset, the bumpless-`ki` property, axis independence, yaw-never-integrates — and `ki_roll`/`ki_pitch` join the live gains panel.

**Root-causing the roll oscillation — it was the estimator, not the gains.** A stubborn ~3–4 Hz roll limit-cycle survived every P/D value tried. The breakthrough was a **rate-vs-angle phase** measurement added to the analyzer: angle is the integral of rate, so a gyro must lead its own attitude by +90°; the roll estimate was lagging by ~+150° — ~60° of excess phase, which turns proportional feedback into positive feedback at the oscillation frequency. The cause was the complementary filter's gyro/accel **crossover sitting at ~3.25 Hz**, right on the control band, so motion-coupled accelerometer noise distorted the estimate exactly where it mattered. Raising the filter coefficient (α 0.98 → 0.998) dropped the crossover to ~0.3 Hz; roll gyro σ fell ~5× and the ring collapsed. No gain change could have fixed it — wrong tool, wrong layer.

**Gyro-bias calibration.** Lowering the crossover exposed a latent ~0.9 deg/s **gyro bias** on pitch, which a complementary filter converts into a steady attitude offset (θ = α·b·dt/(1−α)) that grows with α — surfacing as a visible 0.3° pitch lean. The startup calibration now zeroes the **gyro bias** alongside the accelerometer offset (the gyro-bias zeroing [ADR 0022](decisions/0022-attitude-estimation-complementary-filter.md) already called for), which both removes the offset and frees α to go lower for motion rejection with no bias penalty.

**Flight-analysis tooling.** A raw capture is illegible by eye, so the ground station's `analyze` binary grew teeth: a detrended, windowed **periodogram** for the dominant oscillation frequency and amplitude per axis (with a Nyquist caveat, since the ~90 Hz telemetry cannot resolve above ~45 Hz); the **rate-vs-angle phase** cross-spectrum above; per-row **gains logging** so every capture is self-documenting; and **flight-segment isolation** — the longest sustained-throttle window pulled out and reported on its own, because a whole capture blends ground handling, aborted attempts and the throttle chop with the brief airborne time and the aggregate hides it. The ground station itself gained a **pause + box-zoom** on the live plot for inspecting a frozen snapshot.

**First flight, and the asymmetric tune.** With the estimator fixed and the integral trimming, the bench tune settled — and it **flew**, first tethered, then untethered on its own micro:bit battery. Free flight revealed what the bench (and the incidental damping of the USB tether) had hidden: roll is far livelier than pitch, because the frame is long in X with the battery along it, so I_yy ≫ I_xx and the same gains that are calm on the heavy pitch axis drive the light roll axis unstable. The fix is a **gain asymmetry to match the inertia asymmetry** — `kp_roll` softened to 0.1 while pitch stays 0.2.

**What grounded it.** The untethered hops also exposed the airframe: a persistent front-left (M4) thrust deficit the controller burns authority to trim (it survived a fresh set of props, so it is a motor/ESC/mount issue, not props), and — found last — **two cracked right-hand struts** giving the airframe flex. A non-rigid airframe violates the rigid-body assumption the whole controller rests on (thrust vectoring plus a structural resonance the loop can excite), so tuning is paused until the struts are repaired and the front-left corner is understood. Real progress all the same: it flies, both axes hold attitude in the air, and the tooling now reads every hop honestly — the remaining work is mechanical.

## 2026-08-05 — Arming, runtime gain tuning, a gyro D-term filter, and airframe v3

Three strands landed together: a real arm/disarm sequence, live gain tuning from the ground station, and the D-term noise filter that makes closed-loop tuning viable — plus the third airframe iteration.

**Arming and disarming.** The supervisor state machine ([ADR 0017](decisions/0017-supervisor-failsafe-state-machine.md)) gained an explicit `Disarmed` state between `Initialising` and `Armed`, replacing the previous behaviour of arming on the first command received. Arming now takes a deliberate two-phase stick gesture — throttle held at zero with yaw full-right for ~500 ms, then yaw returned to centre — so the motors cannot spin the instant a packet arrives. Disarming mirrors it (throttle zero, yaw full-left) and reacts immediately. `Degraded` (loss-of-link) now recovers to `Disarmed` on a zero-throttle command rather than re-arming directly, and a safety timeout auto-disarms after 100 s of idle throttle so the craft can't sit armed unattended. The mixer short-circuits to zero motors whenever throttle is zero, and a `debug_assert` in the supervisor task enforces the invariant that a `Disarmed` state never emits a non-zero motor command. A coloured drone-state badge on the ground station makes the current state unmissable.

**Runtime gain tuning.** Reflashing to change a gain is a dead end, so the PD gains and limits became a runtime message. The ground-station-to-drone wire type was refactored from the flat `GroundstationCommand` into a `Command` enum (`PilotCommand` / `ControlModeUpdate` / `ControlSystemParameterUpdate`), carried over the radio inside a new `RadioMessage { sequence_count, command }` — moving the sequence counter out of `PilotCommand` (a transport concern) and the control mode into its own occasional message rather than riding every stick frame. The ground station gained a collapsible gains panel: sliders for every gain and limit and a "Send to drone" button that pushes a parameter update live. The drone routes each `Command` variant to its own `Watch` signal; the control loop reads the latest parameters every tick. Because the remote resends the last value each 10 ms until the sticks next move, a parameter update is naturally retransmitted a few times — implicit acknowledgement on a lossy link, for free.

![Ground station gains panel: the Control System Parameters section expanded with sliders for kp/kd on each axis and the tilt/rate limits, a Send-to-drone button, and the coloured drone-state badge above the live telemetry plot.](images/groundstation%205.png)

**Gyro D-term low-pass filter.** Closed-loop runs were rough because the D term differentiates the gyro, amplifying motor-vibration noise into the motor command. A first-order PT1 filter (pure, host-tested in `firmware-drone-core` — seven tests covering DC gain, monotonic step response, Nyquist attenuation and an exact hand-derived sample) now filters each gyro axis before it reaches the controller, in the control-loop task so the attitude estimator keeps its unfiltered gyro (filtering there would add lag to the estimate). Cutoff is 100 Hz against the confirmed 1 ms (1 kHz) sensor cadence. The starting default gains were also made sane: the D-normalisation rate was 20 dps (absurdly twitchy) and is now 400 dps; yaw rate limit went from 20 to 180 dps; a conservative `kd` of 0.05 replaces the old 0.4.

**Airframe v3.** The third printed airframe iteration packages the build sensibly — a base for the LiPo, provision for a removable lid, and a proper IMU mount, with the IMU soft-mounted on adhesive putty for vibration isolation (the mount rigidity and squareness matter more than the damping, since a skewed mount is a static attitude bias).

## 2026-07-28 — First complete quad airframe, and accelerometer level calibration

The airframe became a **quad**. The single motor-mount plate grew into the first complete 3D-printed quad-X frame — the in-house PETG design of [ADR 0019](decisions/0019-airframe-class-3in-4s-printed.md) — carrying all four iFlight XING2 1404 motors, with a two-tier body housing the micro:bit and the 4-in-1 ESC below the motor deck and the [ADR 0023](decisions/0023-motor-numbering-layout-rotation.md) motor numbering and props-out rotation directions marked on it by hand.

![The first complete 3D-printed quad-X airframe: all four iFlight XING2 1404 motors mounted on a blue printed frame, no propellers, hand-marked with motor numbers and rotation arrows, wired to a bench power supply.](images/first%20quad%20mount.jpg)

On the firmware side, the IMU task gained a **startup accelerometer calibration** that zeroes the sensor's mounting misalignment at the source. It averages ~100 resting accel samples at boot, then subtracts the resulting X/Y offset from every published sample — leaving Z (gravity) untouched, since zeroing the gravity axis would delete the estimator's only down-reference. A resting capture on this build measured the mount at roughly +0.09 g / −0.06 g (≈ +3.1° roll, +5.1° pitch); correcting it at the source means the estimator, controller, and telemetry all agree that a level craft reads zero. The offset is a typed `Acceleration` (a new `Sub` impl, per [ADR 0016](decisions/0016-newtype-per-physical-quantity.md)), and calibration reads retry on error rather than panicking. The same resting capture confirmed a pristine motors-off noise floor (accel σ ≈ 0.9 mg, gyro σ ≈ 0.04 dps), the direct evidence that the earlier closed-loop instability was motor vibration and bench-PSU power, not the sensor — both written up in [imu-vibration-and-bench-psu-power.md](learning/imu-vibration-and-bench-psu-power.md).

## 2026-07-22 — Control loop closed: angle-mode PD, mode toggle, and a bench-rig reckoning

The loop is **closed**. A single-loop PD controller ([ADR 0024](decisions/0024-control-law-angle-mode-pd.md)) turns the attitude estimate and pilot command into the mixer's roll/pitch/yaw demand — angle mode on roll/pitch (stick sets a target tilt against the estimate), rate mode on yaw (stick sets a turn rate against the gyro), derivative on the measured gyro rate to avoid kick, per-axis error normalised so `KP`/`KD` are dimensionless. It is a pure `control_system` function in `firmware-drone-core` (host-tested for signs, damping, axis independence and saturation), driven by a single-publisher stage that owns a `ControllerDemand` `Watch`; the supervisor mixes that demand while Armed and overrides it in the failsafe states, replacing the earlier raw-stick passthrough. That last change rippled into the supervisor's `step` signature and its whole test suite (Armed now mixes the controller demand, not the pilot command).

A remote **control-mode toggle** rides alongside it: a new `ControlMode { Manual, Stabilized }` on both `GroundstationCommand` and `PilotCommand`, flipped by the gamepad's triangle button, switches the drone between closed-loop (Stabilized) and open-loop raw-stick passthrough (Manual). Manual mode exists mostly as a diagnostic — it exercises the plant with the loop broken. To see inside the loop, the telemetry frame gained the `ControllerDemand` and the four mixed `MotorCommand` outputs, both plotted live on the ground station next to the attitude and raw IMU traces.

Wiring that telemetry surfaced a latent bug of exactly the kind [postcard-maxsize-sizing-buffers.md](learning/postcard-maxsize-sizing-buffers.md) warns about: the ground station's receive `CobsAccumulator` was hard-coded to 64 bytes while every other buffer sized itself from the shared `FRAME_MAX_SIZE_BYTES` const. The old frame was ~62 B — one field from the edge — so adding the controller demand tipped it over and the ground station silently dropped **every** frame (an over-full accumulator never emits a decode). Fixed by sizing it from the const, and the two remaining hand-picked command buffers were hardened the same way so the class of bug is closed.

Then the first real closed-loop bench run went sideways — and the lesson was that the newest code (the PID) was **not** the culprit. The instability was the test rig: a hard-mounted IMU fed motor vibration into the gyro (amplified by the D term into noisy demand), and a bench PSU could not power the motors — brownout under load, plus it cannot sink the motors' regenerative current, so every throttle-down tripped its over-voltage protection and cycled the output relay, rebooting the ESC. Manual mode proved the mixer and motor mapping were correct throughout. Both gremlins are written up in [imu-vibration-and-bench-psu-power.md](learning/imu-vibration-and-bench-psu-power.md); the fixes (soft-mount the IMU, run the motors off a battery) wait on parts — the LiPos were never ordered. Gains are untuned until the rig is sound.

## 2026-07-21 — Attitude estimate: complementary filter, fused and plotted

The IMU's six axes are now fused into a live roll/pitch **attitude estimate**. A complementary filter — a fixed-gain blend that high-passes the gyro (smooth but drift-prone) and low-passes the accelerometer (noisy but absolute) — runs as a pure, host-tested type in `firmware-drone-core`, driven by a single-publisher `attitude_estimator` Embassy stage per [ADR 0022](decisions/0022-attitude-estimation-complementary-filter.md). The stage reads the IMU `Watch` (`changed()`-paced, off the IMU's fixed-cadence `Ticker`), steps the filter with a `dt` measured from `Instant` deltas, seeds from the accelerometer on the first sample (no startup slew), and publishes an `Attitude` (roll/pitch angle newtypes, degrees) that the telemetry aggregator samples and sends back. The ground station plots it in degrees: tilt the drone by hand and the fused traces track the tilt — smooth and drift-free — next to the raw accel (noisy) and gyro (drifting), showing what the fusion buys. Angles are held in degrees end to end (the gyro reads deg/s, so the prediction step needs no unit conversion); the `atan2` sign conventions are FRD-native to match the specific-force reading (`az = −1 g` when level).

Two bugs made the trip instructive, both written up. The estimate seeded **NaN on hardware but not in host tests**: micromath's `atan2` returns NaN at the origin where std returns 0, and the IMU's all-zero startup default fed it a zero-length gravity vector; fixed by making the default a physically valid level reading and scrubbing NaN at the angle-newtype boundary ([micromath-atan2-nan-and-valid-seeds.md](learning/micromath-atan2-nan-and-valid-seeds.md)). Separately, changing the `Telemetry` wire format silently broke the ground station until the drone was reflashed — and surfaced that the workspace-excluded `groundstation` crate is never compiled by `cargo --workspace`, so a shared-type rename can land committed-but-broken there.

Also this stretch: the axis command newtypes were renamed `Roll`/`Pitch`/`Yaw`/`Throttle` → `RollCommand`/… to read distinctly from the new `*Angle` estimate types; the X-quad motor mixer and a loss-of-link failsafe ladder ([ADR 0023](decisions/0023-motor-numbering-layout-rotation.md), [ADR 0017](decisions/0017-supervisor-failsafe-state-machine.md)) went into the supervisor; and a bench session nailed down the motor wiring (an as-built 180° channel reversal, corrected in firmware) and the IMU mount orientation. The control loop is still open — the estimate feeds telemetry only; a PID between it and the mixer is next.

## 2026-07-09 — Brushless ESC bring-up: non-blocking 400 Hz servo PWM

The motor output moved from a brushed motor on an H-bridge to a real brushless ESC. The four PWM0 channels now emit standard RC servo-PWM — a 1–2 ms pulse encoding 0–100 % throttle — at a 400 Hz frame, feeding a Sequre Blueson A1 (AM32) 4-in-1 ESC and an iFlight XING2 1404 brushless motor ([parts list](../hardware/electrical/parts-list.md)). 400 Hz is the practical ceiling for 1–2 ms servo PWM: the frame has to clear the 2 ms maximum pulse plus a low gap, so ~490 Hz is the hard edge and 500 Hz would leave no gap at full throttle.

Getting there meant replacing the motor driver wholesale. The first cut used embassy-nrf's `SimplePwm`, whose `set_duty` busy-waits a full PWM period whenever the peripheral is enabled — and `SimplePwm` enables at construction. At a 20 ms (50 Hz) frame those waits, running in the four `set_duty` calls inside `Board::new`, blocked for ~80 ms before a single task was spawned, so every task appeared not to start. The fix was `SequencePwm` in infinite-loop mode: EasyDMA loops over a `static [AtomicU16; 4]` duty buffer forever, and `set_throttle` does one non-blocking atomic store that the DMA reads at the next period boundary, so the CPU is never parked mid-frame. The single `unsafe` — handing the atomic buffer to the driver as a `&[u16]` — is contained and documented; the embassy examples only cover one-shot or PPI-toggled sequences, not continuous in-place duty updates, so this is a small extension of the sanctioned patterns.

On the scope the signal is clean: ~1 ms idle pulse, ~2 ms at full throttle, steady 400 Hz frames, with the pulse width correctly independent of the frame period. At boot every channel holds a zero-width (motors-off) pulse until commanded.

## 2026-06-27 — IMU bring-up, six-axis telemetry, four motors validated

The drone gained its primary sense of orientation. The ICM-42688-P ([ADR 0003](decisions/0003-imu-icm42688-spi.md)) is now driven over SPI from the BSP: a manual chip-select with `transfer_in_place` register access, a WHO_AM_I identity check, power-up via `PWR_MGMT0` (accelerometer and gyroscope in low-noise mode), then a 12-byte burst read from `ACCEL_DATA_X1` that yields all six axes in one transaction. The raw `i16`s are scaled to physical units — g and deg/s — and carried as `Acceleration` / `AngularRate` newtypes inside a new `ImuData`, telemetered through the existing aggregator and surfaced on the ground station, which now plots the three accelerometer traces live alongside the command axes (gyro opt-in) and tabulates all six. On the bench the accelerometer reads ~1 g on whichever axis faces down and the gyro tracks rotation, confirming both scaling and sign.

The four-motor output path was also validated end-to-end: all of `Motor0`–`Motor3` on PWM0 (`P0.10 / P0.09 / P0.12 / P0.02`) spin on the correct corner, defaulting to off at boot through the inverted-duty convention. The ground station picked up some quality-of-life polish too — it now persists the configured serial port and auto-connects on launch (eframe storage).

## 2026-06-26 — CPU-load profiler, and a postcard buffer-overflow fix it exposed

The drone gained a CPU-load measurement with no OS to ask. A sole lowest-priority, thread-mode `load_profiler` task busy-spins a fixed, calibrated chunk of work and infers system load from how much that window stretches under preemption (`load = 1 − T0/T1`); the result rides in each telemetry frame and is plotted by the ground station. The method, its sharp edges (the spinner must be alone and never `.await`, `black_box`/`inline(never)` to stop the optimiser, defmt's missing float precision and the basis-point trick, the cooperative-starvation cliff) are written up in [cpu-load-profiling-idle-spinner.md](learning/cpu-load-profiling-idle-spinner.md).

Adding the `cpu_load` field to `Telemetry` then surfaced a latent fault: the serialized frame outgrew a hand-picked `[0u8; 32]` buffer and `to_slice_cobs(...).unwrap()` hard-faulted the remote mid-link. It was intermittent because postcard varint-encodes the `u32` sequence number — the frame fit at boot and only overflowed once the counter widened at runtime. Fixed by deriving postcard's `MaxSize` on the wire types and sizing every TX/RX buffer from compile-time `FRAME_MAX_SIZE_BYTES` consts, so a new wire field now grows every buffer automatically. Written up in [postcard-maxsize-sizing-buffers.md](learning/postcard-maxsize-sizing-buffers.md).

## 2026-06-21 — Pilot roll/pitch/yaw, gamepad sticks, four-axis plot

The pilot command grew from throttle-only to full attitude. `firmware-types` gained `Roll`, `Pitch` and `Yaw` — normalised −1..+1 deflection newtypes that scrub NaN and clamp at the wire boundary like `Throttle`, kept as three parallel hand-written types rather than a macro (per [ADR 0016](decisions/0016-newtype-per-physical-quantity.md)). They ride in both `PilotCommand` and `GroundstationCommand`; the remote decodes all four axes from the ground-station frame and fans them into per-axis signals, and the drone echoes them back in telemetry. On the PC, the `groundstation` gained sliders for the three new axes and a PlayStation gamepad mapping: Mode 2 sticks (left X → yaw, right X → roll, right Y → pitch) with throttle staying on the right trigger so a self-centring stick can't sit at half-throttle. The live plot now shows throttle, roll, pitch and yaw; the internal-temperature trace was dropped as no longer useful. Frames (body FRD, world NED), sign conventions and the raw-deflection command model were settled first in [ADR 0021](decisions/0021-coordinate-frames-and-command-semantics.md). ## 2026-06-20 — Full round trip, live plot, 100 Hz, gamepad input

The loop is closed and visible. Telemetry now flows all the way back to the PC — the remote's `serial_link_tx` task forwards each `TelemetryState` out the UART using postcard + COBS framing ([ADR 0018](decisions/0018-pc-link-uart-postcard-cobs.md), now in real use, not just throttle), and the `groundstation` decodes it and plots throttle, temperature and drone-state as live time series with [`egui_plot`](https://github.com/emilk/egui_plot) (per-signal show/hide, clear, latest-frame readout). A dedicated `telemetry_aggregator` task on the drone is the sole publisher of `TelemetryState`, tick-sampling its sources and stamping the sequence number ([ADR 0020](decisions/0020-telemetry-aggregator-single-publisher.md)). Cadence pushed to **100 Hz** end-to-end — aggregator, radio round-trip and UART all run on a 10 ms tick (UART ~18 % utilised), and the plotted throttle is butter-smooth despite the value crossing UART → IEEE 802.15.4 → drone → aggregator → radio → remote → UART on every frame. Finally, the throttle source can now be a **Bluetooth gamepad**: the groundstation reads it via [`gilrs`](https://gitlab.com/gilrs-project/gilrs) and maps the right trigger (analog 0.0–1.0) onto the throttle the slider used to own.

## 2026-06-14 — Telemetry pipeline drone → remote

First payload flowing the other way. A new `telemetry` task on the drone reads the nRF52833 internal TEMP sensor at 2 Hz, converts the `I30F2` fixed-point reading to `f32` °C, and broadcasts a `TelemetryState` (sequence number + temperature) on a `Watch`. `remote_link` subscribes and ships the latest sample back to the remote in the radio reply to each `PilotCommand`, so the previous hard-coded placeholder telemetry is gone. Half of the round-trip chain is real now; forwarding the value out the remote's UART to the groundstation, then plotting it, is next. Alongside the feature: per-role state enums (`DroneState`, `RemoteState`) promoted into `firmware-types`, and the per-firmware signals layout settled into one-file-per-signal under `crates/firmware-<role>/src/signals/<name>.rs` so signal modules never define wire types inline.

## 2026-06-09 — PC ground-station controlling motor speed

First end-to-end pilot input. A new host-only `groundstation` crate (binary `gs`) opens an [egui](https://github.com/emilk/egui) window with a single throttle slider; dragging it sends the value as ASCII over USB-CDC at 115 200 8N1 to the remote micro:bit. On the remote, `serial_link` parses the line and publishes a `Throttle` to a `Watch`; `drone_link` subscribes and replaces its self-incrementing test counter with the live slider value. ## 2026-06-02 — Supervisor failsafe wired in

The `supervisor` task now sits between `remote_link` and `motor_controller` and is the sole publisher of motor commands ([ADR 0017](decisions/0017-supervisor-failsafe-state-machine.md)). Loss-of-link is detected when no `PilotCommand` arrives for 100 ms (10 ticks of a 10 ms ticker), at which point the supervisor publishes a zero-throttle `MotorCommand` and flags `SystemState::Degraded`. Verified on the bench: powering off the remote stops the motor within ~100 ms. New host-testable crate `firmware-drone-core` exists for the pure state-machine logic; the actual `Initialising`/`Armed`/`Degraded`/`Fault` machine and ramp-down behaviour are next.

## 2026-06-01 — End-to-end throttle control on hardware

The remote sweeps a `Throttle` value, ships it inside a `PilotCommand` over the IEEE 802.15.4 link ([ADR 0014](decisions/0014-radio-protocol-ieee802154.md)), the drone's `remote_link` task republishes via `Watch<PilotCommand>` ([ADR 0013](decisions/0013-async-communication-primitives.md)), and the `motor_controller` task drives a brushed motor through the L9110 H-bridge via the nRF PWM peripheral.
